Automated CI/CD Implementation

1. CI/CD architecture overview

The implementation extends the Assignment 1 Flask application in BitsDevopsProject. Its member registration, workout recording, dashboard and SQLite persistence remain intact. The assignment entry point, ACEest_Fitness.py, delegates to the existing application factory. New liveness and release endpoints support orchestration and identification of the actual version receiving requests.

GitHub push / pull request
  -> Jenkins: checkout exact commit -> build non-root Docker image
  -> Ruff + containerized Pytest + real NGINX routing integration
  -> SonarQube scan -> enforced quality gate
  -> Docker Hub: immutable version/build/commit image tag
  -> Kubernetes: deploy image digest -> readiness and smoke checks
  -> promote or restore saved deployment and routing state

Jenkins polling provides a fallback for GitHub webhooks. Tests run inside the same image that is published, avoiding dependency differences between CI and deployment. Coverage includes branches and must reach 90% for the application. SonarQube is a separate gate: only successful tests and an accepted analysis permit image publishing. Credentials are supplied by Jenkins, never embedded in application files or committed to source control.

Kubernetes hosts two replicas per application slot: blue, green, candidate and rolling. A two-replica NGINX router exposes all strategies through distinct API prefixes. Startup, readiness and liveness probes have separate purposes. Rolling updates retain ready replicas; graceful shutdown allows in-flight requests to finish. Immutable routing ConfigMaps preserve the configuration required to roll back the router itself.

Version control and artifacts

The original release remains reproducible at Git commit 0cfe471. VERSION records the Assignment 2 release, while versions.json maps versions to their implementation. New work belongs on a feature branch and is reviewed through a pull request; annotated release tags are created after merge. Jenkins archives test results, coverage, the genuine Sonar report, the pushed image digest, deployment evidence and a previous-release rollback snapshot.

The architecture is implemented in source. Local validation is not a substitute for successful hosted Jenkins executions, public registry images or a publicly reachable Kubernetes endpoint.

2. Progressive delivery and resilience

Strategy / endpointImplementation and recovery
Rolling
/rolling/		Two replicas with maxUnavailable=0 and maxSurge=1. Readiness gates replacement pods; failure restores the previous Deployment spec and image.
Blue-green
/blue-green/		Prepare and verify the inactive color, then switch the stable Service selector. The old color remains available for recovery; rollback restores the original selector.
Canary
/canary/		NGINX routes 10%, then 50%, then 100% of requests to candidate. Each stage samples 200 requests and pauses. Successful validation promotes stable and returns the canary route to stable.
Shadow
/shadow/		Stable responds to the user. Only GET/HEAD requests are mirrored to candidate; mirrored responses are discarded. Mutations are not replayed.
A/B
/ab/		Initial 50/50 cohort allocation with a sticky aceest_variant cookie. Stable and candidate remain separately addressable; this is routing validation, not a powered business experiment.

3. Challenges and mitigation strategies

Consistency across versions. Separate ephemeral SQLite files would lose registrations when traffic switches. All application slots instead mount one persistent volume and are pinned to exactly one labelled Minikube node. A 30-second database lock timeout handles concurrent local writers. This intentionally demonstrates application availability on a single node, not multi-node high availability. Production requires an external database and backward-compatible migrations; SQLite must not be shared over NFS.

Safe routing and rollback. Deployment names alone do not establish a strategy. Real NGINX rules implement per-request weighting, cookie-based cohorts and read-only mirroring. Integration testing uncovered a rewrite-order bug: a rewrite with break skipped subsequent backend assignment. Moving assignment before the rewrite fixed the root cause. Previous application specs, Service selector and router configuration are saved before deployment. Failed rollout or smoke validation triggers explicit restoration and a nonzero exit, never a success-shaped fallback.

Environment and evidence limitations. Docker was available, but no Kubernetes context or hosted Jenkins installation was configured. Reproducible Minikube, Jenkins and SonarQube instructions therefore accompany the implementation. Public endpoints, registry credentials and real Jenkins run evidence must be supplied by the owner. Host-only Minikube addresses do not automatically become reachable from a remote Linux Jenkins agent.

4. Key automation outcomes and validation

  • Application reliability: 43 containerized Pytest cases passed, covering inherited behavior, release metadata, liveness, manifest validation, inactive-color selection and failed-rollout recovery.
  • Coverage: measured application branch-inclusive coverage is 93.63%, exceeding the 90% test threshold. Infrastructure scripts have focused unit and integration validation rather than being counted as application coverage.
  • Real traffic behavior: 200-request routing checks passed at 0%, 10%, 50% and 100% canary settings. The 100% stage sent every request to candidate. Exact intermediate percentages are probabilistic.
  • A/B and shadow safety: repeated cookie A/B requests stayed on the selected release. Candidate logs confirmed mirrored reads and no replay of the tested shadow write. Twenty concurrent member registrations were visible across version routes through the shared database.
  • Static analysis: SonarQube 26.11 measured 93.6% coverage, zero bugs and zero duplication. The strict gate is blocked by one inherited CSRF finding, preserved for manual review at the owner's request. Full, genuine evidence is in reports/SONARQUBE.md and the raw JSON.
  • Traceability: Jenkins builds use commit-linked immutable image tags, deployment uses the registry digest, and every deployment saves an explicit recovery artifact. Test or quality-gate failure blocks release.
